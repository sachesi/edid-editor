# Contributing

Bugs and ideas go to the [issue tracker](https://github.com/sachesi/edid-editor/issues);
security problems do not, see [SECURITY.md](SECURITY.md). An EDID that is shown wrong
helps most as a hex dump (`edid-decode` prints one) with the serial number removed.

Before a change goes in:

- `meson test -C builddir` passes, with the compiler reporting no warnings. CI builds
  and runs the tests other than those of the interface on Fedora 44 for every push and
  pull request.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/):
  `fix:`, `feat:`, `docs:`, `test:` and so on, with a subject that says what changed for
  someone using EDID Editor.
- Behaviour described in `docs/` changes with the code that implements it.
- EDIDs added to the tests come from a public source that allows it, with serial
  numbers removed; `core/tests/corpus/README` says how.

## Where things are

    meson.build              project, GTK and libadwaita dependencies
    core/                    the EDID model, from wxEDID, built as a static library
      EDID_main.cpp          parsing and assembling of the whole EDID, value names
      EDID_base.cpp          base block groups: header, basic parameters, timings
      EDID_dsc.cpp           the 18-byte descriptors of the base block
      CEA.cpp, CEA_ET.cpp    CTA-861 data blocks, and those with an extended tag
      DisplayID.cpp          DisplayID 1.x and 2.x blocks
      grpar.cpp              groups of fields and their arrays
      vmap.cpp, vid_fmt.cpp  named values and the VIC and DMT timing tables
      EDID_text.cpp          hexadecimal text import and export, text reports
      EDID_summary.cpp       the facts listed on the Overview
      EDID_compare.cpp       field by field comparison of two EDIDs
      EDID_display.cpp       connected displays under /sys/class/drm
      wxcompat.h             the small part of wxString and wxArray the core uses
      rcode/                 result codes and the generator of their scope table
      tests/                 core tests, sample EDID generator, real EDID corpus
    app/                     the GTK application
      window.cpp             the window: sidebar, field cards, timing editor, dialogs
      style.css              structural CSS, colors come from libadwaita
      tests/test_ui.py       tests of the interface through AT-SPI
      io.github.sachesi.EdidEditor.*  desktop entry, AppStream metadata, icon

Each part of an EDID is a group (`edi_grp_cl`) holding fields (`edi_dynfld_t`). A field
names its bytes and bits, flags such as read-only or value list, and a handler that
reads or writes it as text or as a number (`OP_READ`, `OP_WRSTR`, `OP_WRINT`). The
application builds every card from these descriptions, so a new decoder in the core
shows up in the editor; `app/window.cpp` only adds plain names for its fields. Handlers return an `rcode`, the result
type of the rcode library; its scope table, `wxedid_rcd_scope.cpp` and `.h`, was
generated by `rcode/rcd_autogen.gen`.

## Running

    meson setup builddir
    meson compile -C builddir
    builddir/app/edid-editor [FILE]
    meson test -C builddir --no-suite ui    # the core tests and the metadata validators
    meson test -C builddir --suite ui       # the interface tests, a few minutes

The interface tests start the application in a headless Weston session with Xwayland and
drive it through the accessibility tree, because keyboard and pointer events do not
reach that session. Each scenario has its own runtime directory, so nothing is read from
or written to your recent files and settings. A scenario fails on a GTK, libadwaita or
GObject critical in the output of the application, not only on a failed step.

The corpus test round-trips real EDIDs byte for byte, and several tests expect the
values `edid-decode` prints for the same data; a decoder change that departs from them
needs a reason from the standard.
